# Meshtastic decoding parity with OpenWebRX+

This report covers card t_361d81c7, branch `feat/meshtastic-iq-parity`. It
compares the app's integrated native Meshtastic backend with the OpenWebRX+
Meshtastic chain, using the same IQ files.

## Result

18 out of 18 same-IQ comparisons pass. Each IQ file is a 1 MS/s complex-f32
recording. Both chains read the file:

- OpenWebRX+ chain: the unmodified upstream `lorarx` (oracle build of the
  vendored author-site source), run with the exact `MeshtasticDemodulator`
  argv. Its JSON line is passed through the unmodified OpenWebRX+
  `owrx/meshtastic.py` `MeshtasticParser.parse()`.
- Native chain: `sdrcore_meshtastic_replay` feeds the same file through the
  registry `meshtastic` backend, which is the code the app runs. That backend
  is the embedded lorarx followed by the native `PacketParser`.

For each frame the harness checks:

- Detection: exactly one lorarx frame, and exactly one native event when the
  CRC is good.
- Bytes: the base64 payload from lorarx equals the transmitted Meshtastic
  frame byte for byte.
- PHY: `sf`, `cr`, `bw` and `net` (sync word 0x2B = 43) match the transmitted
  settings. The native `phy` has the same `crc`, `sf`, `cr`, `invers`,
  `preamb`, `duration`, `afc` and `fec` as lorarx. Native `bw` is lorarx Hz
  divided by 1000 (kHz).
- Levels: `snr`, `level`, `nfloor` and `pknfloor` are exactly equal, with no
  tolerance. The native backend copies lorarx's parsed doubles unchanged.
- CRC: a frame with three zeroed data chirps gives `crc:0` in lorarx. Both the
  OpenWebRX+ parser and the native backend drop it. The bytes lorarx decoded
  in that case differ from the transmitted frame, which is expected.
- Decryption: the native event is `encrypted:false`, and its `type` equals the
  OpenWebRX+ `type`.
- Decoded fields: every field OpenWebRX+ emits from this list must exist in
  the native event and be equal (numbers within 0.001): `mode`, `src`, `dst`,
  `comment`, `freq`, `type`, `message`, `lat`, `lon`, `altitude`, `battery`,
  `uptime`, `channelUse`, `airtimeUse`, `weather`, `data`.
- Header fields that OpenWebRX+ does not output (`packet_id`,
  `channel_hash`) are checked against the transmitted header bytes.
- Timestamps: both are wall-clock milliseconds taken when the frame is parsed,
  and each call reads the clock separately. The check is that the native
  `timestamp` is within 30 s of the harness clock and of the OpenWebRX+
  `timestamp`. Exact equality is not possible: OpenWebRX+ itself stamps
  `datetime.now()` at parse time.

Coverage: every preset the app accepts (all firmware presets except LongSlow
SF12 and Tiny 15.6 kHz, which are outside the OpenWebRX+ chain), the four
bandwidth indices 6/7/8/9, SF7–SF11, CR 4/5, 4/6 and 4/8, the default key,
AES-128, AES-256, and a CRC failure. CR 4/7, no-CRC headers, sync word 0x12,
noise and a +20 kHz offset are covered at PHY level by the existing
`sdrcore_lorarx_parity` (20 cases, byte-identical JSON).

For non-LongFast presets, the real on-air frame keeps its original ciphertext
and nonce. Only header byte 13 (channel hash) is recomputed for the preset
name with the default key, because the firmware and the native parser only
try a channel whose hash matches. The OpenWebRX+ parser ignores the hash.

## Capture sources

- Packet bytes: `native/tests/data/meshtastic_vectors.json`. Two kinds:
  - `real_meshtastic_sdr_text` is a real over-the-air LongFast packet
    published by meshtastic_sdr (GPL-3.0, commit 2ff1a68).
  - The others are generated by `native/tests/meshtastic_oracle.py` with the
    official Meshtastic protobufs and the OpenWebRX+ parser at f1e0d1a.
- IQ: generated per case by the vendored, unmodified upstream `loratx`. It is
  deterministic, with `-z 10` padding.
- No real over-the-air IQ recording of Meshtastic exists on this host. Searches
  under `~/prj` found no LoRa/Meshtastic `.cu8`, `.iq` or `.f32` captures; the
  only `*mesh*.cu8` is an Elster rtl_433 test. So parity on air-recorded IQ
  (real multipath, drift, interference) has not been shown. Only the packet
  bytes are real.

## Reproduce

```sh
cmake -S native -B build/meshtastic-parity -DCMAKE_BUILD_TYPE=Release
cmake --build build/meshtastic-parity -j3 \
    --target sdrcore_meshtastic_replay lorarx_oracle loratx_oracle
uv run --no-project --python 3.12 --with meshtastic==2.7.11 \
    --with pycryptodomex==3.24.0 native/tests/meshtastic_chain_oracle.py \
    build/meshtastic-parity/loratx_oracle build/meshtastic-parity/lorarx_oracle \
    build/meshtastic-parity/sdrcore_meshtastic_replay \
    native/tests/data/meshtastic_vectors.json
```

Expected output: one `identical bytes, PHY values, CRC, decryption and OWRX+
fields` line per case, then `bad_crc: corrupted decoded bytes ... dropped by
both parsers`, and finally `PASS: 18 identical-IQ chain comparisons`. The
script needs the OpenWebRX+ checkout at `~/prj/ref/openwebrx/openwebrx-plus`.
It is a host-only oracle, so it is not a CTest: Python and the OpenWebRX+
source are not build dependencies. The app never runs Python.

`sdrcore_meshtastic_replay <iq.f32> <config-json> [freq]` (built only in the
host test block) prints one native `message` event per line. It processes only
full 4096-frame blocks, like upstream `inreform()`.

## Investigated differences

- The first run failed on `bad_crc`, because the harness required the decoded
  bytes to equal the sent bytes. With `crc:0`, lorarx outputs the corrupted
  decode, so the harness was wrong, not the decoder. The check now applies
  only to CRC-valid frames, and the `crc:0` line goes through the real
  OpenWebRX+ `parse()`, which returns `None`.
- Deliberate differences, unchanged from `docs/status/meshtastic.md`: the
  native parser uses the firmware channel-hash key loop, reports a wrong key
  as `encrypted`, and adds header/PHY fields. OpenWebRX+ uses one key, tries
  it regardless of the hash, and adds `color`/`symbol` presentation keys.
  None of these differ for the decryptable packets above.
- UI-visible formatting: `MeshtasticPacket.fromEvent` and the panel are
  tested on real `PacketParser` output (`test/ui/meshtastic_*`). The ctest
  `sdrcore_meshtastic_ui_fixture` checks that fixture against the native
  parser byte for byte. This run did not add a new Dart formatter test;
  the native event fields the UI reads are the ones compared above.

## Not verified

- Over-the-air reception: the RTL-SDR Blog V4 was not attached to the host
  (`lsusb` showed only root hubs and the QEMU tablet), so live LoRa reception
  and a Linux-host receiver/UI session with real packets were not possible.
- Real-air IQ parity: no over-the-air Meshtastic IQ recording is available
  (see Capture sources).
- Running a full OpenWebRX+ server: the comparison uses its real lorarx
  argv and real parser module, but not its csdr input chain or web UI. The
  1 MS/s tap in the app is native (`docs/status/meshtastic-mode.md`), and
  the IQ files here start after that tap.
- Android: the emulator has no USB SDR, so packet decoding and CPU cost on
  Android were not exercised. Real phones are not used (AGENTS.md).
- Licence: no blocker. lorarx is GPL-2.0-or-later
  (`docs/lora-upstream-feasibility.md`), and the OpenWebRX+ parser is used
  only as a host oracle.
- Bandwidth: no blocker at the 1 MS/s tap for any supported preset (500 kHz
  max). LongSlow (SF12) and the Tiny presets stay unsupported, matching
  OpenWebRX+.
