# OpenWebRX+ SSTV source audit and native/UI contract

Status: design/audit only. No SSTV source is embedded and no image reception, host oracle, Android build of FFTW, or hardware SSTV reception is claimed by this card. Downstream native/UI/oracle cards depend on this contract. Source pins: OpenWebRX+ `f1e0d1ac7dfac3732f2981078e8bf7fff63d9764`, csdr-plus `f26b52071c4a127fc8193d058c249cac57585de4` (local reference checkouts). Paths below are relative to those checkouts unless prefixed `native/` or `lib/`.

## Actual chain, options, and receiver boundary

- `openwebrx-plus/owrx/modes.py:238-244` declares `sstv` with underlying `usb`, `lsb`, `nfm`, `service=True`, `squelch=True`. These are *demodulators* that make ordinary real audio, not SSTV picture modes. The bandplan can select LSB; USB is the sensible default, not a mandatory restriction. A selection of the SSTV preview alone must not retune; explicit underlying-demod selection must call the normal centered receiver mode control. A data decoder must not acquire a second tuner or silently change sample rate/frequency.
- `openwebrx-plus/csdr/chain/digimodes.py:180-195` constructs `SstvDecoder(24000, 300000)` -> `SstvParser(service=...)` and returns a **fixed 24,000 samples/s real mono audio** rate. `openwebrx-plus/owrx/dsp.py:161-177,179-218` negotiates this rate into the selector/primary demod and routes the demodulated FLOAT audio buffer into the secondary decoder; `ClientAudioChain` has its own client-rate conversion. `owrx/dsp.py:765-767` selects the chain. There is no upstream manual SSTV image-mode setting: VIS auto-selection is intrinsic. `dbgTime=300000` only controls dormant/debug textual logging, not signal-processing quality. Squelch is supported by the selector (`dsp.py:238-242`), not by a new SSTV control. OpenWebRX+ service mode writes files; client mode emits line updates.
- Our sole receiver produces mono demodulated `value` at variable `if_rate_` in `native/src/dsp/receiver.cpp:684-722`, then the existing 48 kHz stereo audio resampling/deemphasis, AGC, squelch, volume and mute in `:728-796`. Do **not** feed 48 kHz PCM directly to the 24 kHz upstream decoder, or simply reinterpret it as 24 kHz. Add a native, band-limited rate conversion from the same tuned USB/LSB/NFM demod audio to 24 kHz, before user volume/mute, retaining the one audio sink; match OpenWebRX+'s selector/audio conditioning and record the precise tap used. If using post-48-kHz audio, tap before mute/volume and resample properly; note its existing 8 kHz SSB / 4.5 kHz NFM audio low-pass and FM deemphasis. Avoid double squelch/AGC. Ensure decoder disable incurs no extra DSP. A radio already running in an incompatible demod is `not ready`, never an implicit mode change on preview.
- Current registry `native/src/decoder/registry.cpp:12-21` and Dart catalog `lib/ui/decoders/decoder_contract.dart:88-103` misleadingly require USB only and expose `auto`, `martin_m1`, `scottie_s1` despite no implementation of forced VIS. Native selection checks `required_mode` in `native/src/sdrcore.cpp:1133-1134` and Dart in `decoder_session.dart:119-127` (`_canAttach`); both must allow USB/LSB/NFM by one agreed explicit validation rule, rather than setting `required_mode=UINT32_MAX` and accidentally accepting WFM/AM. For v1 settings choose `{"version":1,"settings":{"underlying":"usb","mode":"auto"}}` with underlying in `{usb,lsb,nfm}`; `underlying` is a *request to the UI's normal mode control*, not a hidden native retune. Native selection rejects a config whose underlying demod differs from the currently applied receiver mode, leaving the previous decoder and audio intact. Until a forced-mode algorithm preserving upstream acquisition behavior is implemented and compared, accept **only** `mode=auto` natively and disable/hide other values; persisted old `martin_m1`/`scottie_s1` values normalize to auto, not pretend to work. If native/UI cards agree to implement genuine forced detection, explicitly version/validate the full supported VIS list; do not pass unknown strings through silently. `DecoderSession._drainEvents` (`decoder_session.dart:246-290`) accepts only `kind == message` events and routes them to RDS or rtl_433 (`:279`), and `decoder_panels.dart:50-51` maps `sstv` to `DecoderPlaceholderPanel` with a static "no image" preview (`:469-487`); both need real SSTV image-event routing.
- The existing rtl_433 path processes a tuned complex-IQ branch (`receiver.cpp:320-405`); it is **not** an audio tap. Add `Input::audio` scheduling to that receiver, reusing its `Decoder`, per-handle FIFO, stream-generation and poll C ABI. `native/src/sdrcore.cpp:544` currently zeroes voice audio whenever *any* decoder is selected; change this specifically so SSTV can keep listening, without regressing rtl_433's current mute policy or consuming raw IQ/PCM in Dart. The `sdrcore_decoder_v1.h:55-58` comment already promises no implicit mute and needs implementation/test alignment.

## Exactly what the upstream code can decode

`csdr-plus/include/sstv.hpp:46-74,133-525` declares these VIS IDs; `src/lib/sstv.cpp:102-133` actually instantiates every one listed below, with auto VIS and even parity (`:813-838`). Dimensions are `LINE_WIDTH x LINE_COUNT`; PD modes have `LINE_STEP=2` but still output full-height RGB scanlines. Names in the OpenWebRX+ parser (`openwebrx-plus/owrx/sstv.py:13-38`) are display names, sometimes different from C++ `NAME`.

| Family | VIS -> name (dimensions) |
|---|---|
| Robot | 0 Robot 12 (160x120), 4 Robot 24 (160x120), 8 Robot 36 (320x240), 12 Robot 72 (320x240) |
| Martin | 32 Martin 4 (320x128), 36 Martin 3 (320x128), 40 Martin 2 (320x256), 44 Martin 1 (320x256) |
| Scottie | 48 Scottie 4 (320x128), 52 Scottie 3 (320x128), 56 Scottie 2 (320x256), 60 Scottie 1 (320x256), 76 Scottie DX (320x256) |
| Wraase SC2 | 51 SC2 30 (320x128), 55 SC2 180 (320x256), 59 SC2 60 (320x256), 63 SC2 120 (320x256) |
| PD | 93 PD 50 (320x256), 94 PD 290 (800x616), 95 PD 120 (640x496), 96 PD 180 (640x496), 97 PD 240 (640x496), 98 PD 160 (512x400), 99 PD 90 (320x256) |

Thus **24 mapped VIS entries**, not the historical plan's 15. There is a critical upstream defect affecting the largest one: `sstv.hpp:537,572` allocates `linebuf[2][640]`, but PD 290 has width 800 (`:432-438`), and `sstv.cpp:701-737` indexes/copies 800 bytes per chroma row. The decoder can read/write outside that buffer. Do not ship or test PD 290 with the unmodified upstream bound: raise it to at least the largest mapped width, preserve the actual color algorithm and prove the fix with a PD 290 ASan oracle. If it cannot be fixed and validated, label PD 290 unavailable rather than advertising all 24 as safe. `VIS_AVT90=68` exists as a class/parser label but is explicitly commented out of the mode map at `sstv.cpp:124-125` because quality is poor; it must not be advertised as supported. `owrx/sstv.py:40-63` also labels Robot BW variants, Martin HQ, FAX480, FAST FM, Proskan, MSCAN, Pasokon as *unsupported*; no decoder object is created for them. Other AVT variants are not defined. An unknown VIS or a parity failure returns to header search, not a made-up generic mode. The mode table lives in source, not in the two-value Flutter placeholder dropdown.

## Framing, fidelity, and source dependencies

- `sstv.cpp:39-45,171-304,441-483,813-839`: leader 1900 Hz / break 1200 / leader 1900 / VIS 1200 searched in 2 ms steps with Hann-window FFT peaks; eight 30 ms VIS bits (seven ID bits + even parity). Sync detection follows each mode's timing, and Scottie uses an initial sync. The per-line sync search and timing offset provide horizontal alignment, but **there is no explicit geometric slant-correction API**: do not promise complete clock-drift correction. Missed lines are black-filled, including tail padding on interrupted frames (`:259-291,352-375`). FFT Hann peak/interpolation, mode-specific windows, RGB/GBR/YUV conversion, Robot/PD chroma interleaving (`:507-759`), and actual timings must be retained for fidelity, not reimplemented as a simplified two-mode receiver. Test at least USB/LSB/NFM where actual recordings allow and multiple families/VIS, especially Robot 36/PD 290 and Scottie sync.
- Decoder writes a 54-byte, top-down, 24-bit **BGR BMP** header followed by contiguous `width*3` BGR bytes per row (`sstv.cpp:306-349,623-739`). Header byte 6 is VIS and byte 7 is `0x73`. Max enabled dimensions are 800x616 (one complete raw frame 1,478,400 bytes, one line 2,400 bytes). The parser scans for `BM` or debug ` [` markers; `owrx/sstv.py:111-225` emits header metadata (`mode:"SSTV"`, width, height, `sstvMode`, UTC `%H:%M:%S` timestamp, generated `SSTV-<UTC yyMMdd-HHmmss>[-kHz]` filename and frequency in Hz) followed by one *base64 BGR scanline* event (`pixels`, zero-based `line`, width, height). The browser converts BGR to RGBA (`htdocs/lib/MessagePanel.js:786-823`). Client emits no separate image-complete message: the last line implies completion. Service saves BMP, closes on last row, and converts to PNG; at shutdown `SstvParser.run:109` uses a minimum half-height threshold, while `DataRecorder.closeImage` default minimum is 64 (`owrx/storage.py:197-230`), so half-height partial-file salvage is a service/shutdown policy, not a guarantee that the radio decoded all pixels. Images in a gallery need an explicit `complete` vs `partial` status and must not mislabel padded black lines as received pixels.
- `csdr-plus/src/lib/sstv.cpp` and `include/sstv.hpp` carry Marat Fayzullin's **BSD-3-clause-style** redistribution/endorsement notices (`:1-29`, `hpp:1-29`); preserve them verbatim. `include/module.hpp` and its ringbuffer/reader/writer glue are GPL-3.0-or-later by their file headers, and the csdr-plus root `LICENSE-GPL` is GPL-3. OpenWebRX+ Python parser/chain are in a separately **AGPL-3.0** root (`openwebrx-plus/LICENSE.txt`); implement their observable framing in own GPL app glue, or review AGPL source redistribution if copying code. Do not label every upstream SSTV source as GPL-3 or copy Python verbatim without this distinction. App GPL-3.0-or-later is compatible with BSD-3 and GPL-3; AGPL integration warrants explicit notice review.
- `sstv.hpp:33-35,104-119,526-636` requires FFTW3 single-precision `fftw3f` for per-mode FFT plans, plus csdr `Module<float,unsigned char>` Reader/Writer/ringbuffer glue (GPL-3 header). `csdr-plus/CMakeLists.txt:42-46` requires `fftw3f` **and** `samplerate` for its *whole library*; `src/lib/CMakeLists.txt:18-80` links both. The SSTV translation unit itself does not call libsamplerate: a minimal source-built adapter may omit that dependency if it supplies a verified native 24 kHz resampler and the upstream module IO or a thin compatible adapter. Never drop FFTW and claim identical peak behavior. FFTW3 is GPL-2.0-or-later per [its license](https://www.fftw.org/doc/License-and-Copyright.html), compatible with this GPL-3.0-or-later app when used under GPLv3; keep its source and notice. On this host `pkg-config --modversion fftw3f samplerate` finds neither, and no `native/third_party/fftw3` or NDK FFTW header was found in the checked paths; **this is an unverified build dependency, not a demonstrated licensing or technical impossibility**. Pin a source revision, vendor notices and build `fftw3f` using the app's CMake/NDK for host and arm64, and run the actual build; avoid depending on a host-installed binary in the APK. Its Android threading/planner behavior requires verification. Beware `createPlans` / `destroyPlans` state transitions (`sstv.cpp:776-811`): `createPlans` stores the sample-rate/input/output cache before `destroyPlans` clears it, disabling the intended repeated-call shortcut; test lifecycle under ASan and multiple decoder starts, not just a single happy-path image. The source has variable-length stack arrays and `vsprintf` (`:510,626,388-395`); bound format/debug and stack behavior before shipping while retaining algorithmic equivalence. `decodeLine:575-576` tests output capacity as `width*LINE_STEP` rather than `width*3*LINE_STEP`; preserve row bytes by correcting the guard in a bounded adapter/patch.

## Frozen v1 image event contract for native and UI children

Use the *existing* `sdr_decoder_poll`/`SdrDecoderEvent` (`native/include/sdrcore_decoder_v1.h:14-71`), **not** a second callback/API: `kind=SDR_DECODER_IMAGE_PROGRESS` (2) or `SDR_DECODER_IMAGE_COMPLETE` (3); payload UTF-8 JSON with `source:"sstv", version:1`. One event is <=65,536 bytes, FIFO <=256, sequence monotonically increases per handle, `stream_generation` tags restart and `dropped_events` exposes overflow. Image pixels are decoded output, not raw audio/IQ. This schema makes the completed image an ordered assembly of bounded row events rather than attempting to stuff a 1.48 MB raw BMP into a 64 KiB payload.

For a new image, emit one `image_progress` with `phase:"start", frame_id:<nonzero uint64 identifier serialized as decimal string>, vis:<integer>, sstv_mode:<canonical name>, width:<int>, height:<int>, timestamp_utc:<ISO-8601 UTC string>, frequency_hz:<integer>, underlying:<"usb"|"lsb"|"nfm">, line:null, pixels_bgr_base64:null, padded:null`. Allocate `frame_id` from a per-handle counter that does not reset on deselect/retune; do not let a newly created backend reuse its local first-frame ID. The native handle/adapter, not the source `Decoder::process` signature, stamps the **applied** tuned frequency (`center_frequency_hz + vfo_offset_hz`) when VIS/header is acquired and holds the same frame metadata in subsequent events. Timestamp is capture/header wall-clock UTC, not UI receipt time. A row `image_progress` repeats these fields, uses `phase:"line", line:<zero-based int>, pixels_bgr_base64:<base64 of exactly width*3 BGR bytes>, padded:<bool>`; `padded=true` only for upstream-generated empty replacement/tail rows, not for a valid decoded black pixel row. Instrument the existing `decodeLine`/`printBmpEmptyLines` paths to distinguish them: BMP row bytes alone cannot reveal this distinction. Count `LINE_STEP=2` modes' two actual output rows separately, as the upstream BMP/parser does. Native emits each row in ascending order; no metadata-only percentage substituted for actual rows. Max expected base64 row is 3,200 characters. A line progress event *never* means the picture was saved.

Emit `image_complete` (metadata only, no huge embedded image) with the same source/version/frame/vis/name/dimensions/time/frequency/underlying and `received_lines:<int>, padded_lines:<int>, status:<"complete"|"partial">, reason:<"end"|"sync_lost"|"retune"|"mode"|"stop">`. `received_lines` counts actual row events before the terminator, `padded_lines` counts rows flagged padded; a natural frame end with all rows emitted is `complete` (even if internal missed-sync rows were black-filled, which must remain visible via `padded_lines`), whereas early termination or lost rows is `partial`. Do not emit a `complete` if the last row is missing. The UI assembles BGR into a bounded byte buffer only for one current frame, validates dimensions against the pinned mode (max 800x616 *after the PD 290 buffer fix*), base64 length/line order/frame_id/frequency/generation and `status`/`received_lines`/`padded_lines`. It then converts to display/save format (e.g. PNG). Gallery/session retention must have an explicit small cap (e.g. 8 completed/partial frames plus the current 1.48 MB assembly), and freeing on deselect/dispose must be tested. A partial frame may be saved only with clear partial labeling and no implication of full reception; choosing a half-height threshold as in OpenWebRX+ service is a documented UI policy, not the decoded-image definition.

Reset decoder and clear incomplete UI assembly on retune (including effective VFO change), mode change, stream generation change, source rate change, stop, deselect; never merge old rows into a new image. The C FIFO invalidates on these boundaries (`sdrcore.cpp:98-121,1107-1183`) but its sequence must **not** restart; frame identity and frequency reject late results on same-generation retunes. Nonconsecutive *global event sequence* is normal because RDS/message events share the queue; instead detect a missing `line`, absent `start`, malformed payload or queue loss and mark/drop that frame, never produce a plausible-looking corrupted image. Keep polling after a line gap for a new start. Native should avoid flooding the 256-entry FIFO (one row per event, UI drains promptly; if overflowing count drops rather than silently truncate). Existing `DecoderSession` message polling is rtl_433-only and 500-row messages must not absorb SSTV. On stop the native API currently invalidates the FIFO: a `stop` partial completion is not guaranteed deliverable via poll, so *before* stop either surface an explicit UI partial from retained actual rows, or keep it in a bounded gallery under a clearly partial status. Document/test the chosen behavior. Never call `sdr_decoder_poll` after handle destroy.

Build/test gates for children: compare the **same** 24 kHz mono captures against csdr-plus `csdr sstv`/SstvDecoder offline, checking VIS, row bytes/image pixels, dimensions, time-alignment and explicit completion, including noise/frequency offsets. FFTW availability and generated test fixtures are tasks for the implementation/oracle children, not grounds to substitute another decoder now. Native unit tests cover parity, sync/missing-line handling, retune reset and audio continuity; Dart tests cover event validation/FIFO overflow, preset migration, 344dp and unfolded layout, actual file save; host CTest/ASan, Flutter analyze/tests/Linux build and serialized Gradle debug/release belong to the integration card. No device/audio parity is verified by this audit.
