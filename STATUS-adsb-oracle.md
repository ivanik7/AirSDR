# ADS-B generated-IQ oracle (host)

Source: FlightAware dump1090-fa `0339a57b89cd6e61856cbb13ae342c31ae7be5ac` in `~/prj/ref/openwebrx/ext/dump1090`, GPL-2.0-or-later. The two published DF17 airborne CPR bit patterns (ICAO 40621D) are identified at https://github.com/junzis/pyModeS/issues/68. `native/tests/generate_adsb_iq.py` (GPL-3.0-or-later) constructs new 2.4 MS/s SC16 IQ with Mode S preamble and pulse-position modulation; no recorded IQ, upstream waveform, binary fixture or undocumented third-party license is distributed. Frames are placed at samples 16320/23000 and optionally 33000/48000 to exercise the native decoder's 16384-sample magnitude-block overlap, with irregular process chunk sizes. The 40k/69k complex-sample output is temporary; the CU8 receiver runner quantizes this same SC16 recording to RTL-style unsigned bytes at the receiver ingress. The comparison is over the same synthetic RF symbols, but CU8 quantization means the bytes at the decoder boundary differ slightly from the original SC16.

Repeat (from repo root; build upstream in a disposable directory, not in the reference checkout):

    cp -a ~/prj/ref/openwebrx/ext/dump1090 /path/to/scratch/dump1090
    make -C /path/to/scratch/dump1090 clean RTLSDR=no BLADERF=no ARCH=generic
    make -C /path/to/scratch/dump1090 -j3 dump1090 RTLSDR=no BLADERF=no HACKRF=no LIMESDR=no SOAPYSDR=no ARCH=generic
    cmake -S native -B build/native-host-tests -DCMAKE_BUILD_TYPE=Debug
    cmake --build build/native-host-tests --target sdrcore_adsb_backend_test sdrcore_adsb_tap_test -j3
    python3 native/tests/adsb_iq_oracle.py /path/to/scratch/dump1090 build/native-host-tests/sdrcore_adsb_backend_test build/native-host-tests/sdrcore_adsb_tap_test

The oracle invokes the original binary with `--ifile <generated.sc16> --iformat SC16 --modeac --raw --write-json <dir>`. It compares each raw hex frame in order, the full aircraft ICAO set, accepted message count, barometric altitude, optional lat/lon within 0.00001 degrees, and RSSI within 0.1 dB for both the float decoder adapter and the receiver CU8 raw-IQ tap. Upstream returns status 1 at normal finite-file EOF (`Abnormal exit.`); the harness allows that status only when the raw frames and generated JSON pass every assertion. In this run: 2/2 and 4/4 raw frames decoded in order; the only ICAO is 40621D; two frames yield global CPR (52.26578, 3.938913), 38000 ft, two messages. Four frames yield four messages and 38000 ft, but both upstream and embedded tracking omit the position after a rejected implausible-speed update caused by replaying the identical CPR pair too quickly; this is parity, not a successful second position. RSSI differs by less than 0.1 dB, including CU8 quantization. No single-bit correction is enabled in the OpenWebRX+ invocation or the app; native regression verifies default CRC rejection and separately verifies the upstream one-bit correction algorithm after enabling it temporarily.

Additional native coverage: `sdrcore_adsb_backend` verifies CRC integrity, default rejection/one-bit correction (explicit opt-in upstream core, not a UI option), global and reference-relative/local CPR, 128-track and 65536-byte caps, per-field expiry, 300-second stale removal and an empty subsequent snapshot, and clearing tracks/events on reset. `sdrcore_adsb_tap` covers direct 2.4 MS/s, higher-rate resampling, insufficient bandwidth/window rejection, retune/mode reset, and the new CU8 replay path with a reset. Existing `test/ui/adsb_panel_test.dart` checks the not-ready rate message, explicit rate/tune controls, 344-dp cover width, message-rate display, stale replacement and retune clearing; it was included in the full Flutter test run.

AddressSanitizer found a 2016-byte leak in upstream `crc.c`'s optional correction-table initialization when the test switches from one-bit correction back to default. The vendored `modesChecksumInit` now frees previous tables before replacing them; the decode algorithm is unchanged and the modification is documented in `native/third_party/dump1090/PROVENANCE.md`. Re-run with `-fsanitize=address -fno-omit-frame-pointer` for C/C++ and `-fsanitize=address` at link, `ASAN_OPTIONS=detect_leaks=1:halt_on_error=1`: both the backend CTest and two fixture comparisons passed after the fix.

OpenWebRX+ uses `Convert(COMPLEX_FLOAT, COMPLEX_SHORT)` then the external dump1090 `--ifile - --iformat SC16 --modeac --metric --quiet --write-json` and `AdsbParser` polls JSON; this adapter instead publishes bounded native snapshots. With short finite `--ifile` playback, upstream's `aircraft.json` `seen` field underflows to ~1.84e16 seconds when message timestamps are slightly newer than the immediate JSON write's `now`; `AdsbParser.parseJson` (`owrx/aircraft/__init__.py:719-723`) consequently skips entries because `ts = now - seen <= lastParse`. The executable's JSON aircraft/position are compared directly, not falsely described as a working OpenWebRX+ UI replay. An attempted direct parser import failed because this host's Python 3.14 lacks `distutils`; running the full OpenWebRX+ parser/live FIFO chain on a properly provisioned environment remains unverified. For live streaming, wall-clock scheduling differs from accelerated file playback; receiver timestamps are based on live `mstime` plus sample offset and snapshots every wall second, rather than dump1090's per-read file timestamp and file-EOF JSON. The synthetic fixture covers one ICAO/DF17 airborne CPR only: Mode A/C, surface CPR, multi-ICAO interference, weak-signal/noisy RF, real analog passband, and Android device throughput remain unverified. The host enumerated RTL2838 (`0bda:2838`) but this task did not measure live 1090 MHz reception or attach the phone; no bandwidth defect was established by this test.

Gates in this worktree: full CMake host build and CTest 28/28; `flutter analyze` no issues; `flutter test --concurrency=1` 490 passed / 17 skipped; Linux debug build; Android debug APK and arm64 release APK both built. Phone install/audibility is separate. A synthetic direct-tap oracle cannot prove RF reception or OpenWebRX+ service-process parity.
